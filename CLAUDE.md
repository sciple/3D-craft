# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A lightweight native Windows desktop CAD tool (Rust + Tauri v2 + three.js), inspired by SketchUp's modeling workflow, for one specific use case: modeling small parts to 3D print. It is deliberately not a general CAD replacement — favor the simplest correct implementation over generality or completeness when extending it.

**Keep `README.md` up to date**: it holds the user-facing install/run/operation guide (the tool list, shortcuts, and controls). Whenever a change adds, removes, or meaningfully alters user-facing functionality — a new tool, a changed shortcut/keybinding, a new file-menu action, or a workflow change — update `README.md` in the same change so it stays accurate. Internal refactors with no user-visible effect don't need a README edit.

**Branch large or risky features.** Any change big enough to disrupt pre-existing, working behavior — a new document-model collection, a project-file format change, edits to shared geometry or snapping code, a new tool touching existing ones — must be built and validated on its own git branch first. Only fold it back into `main` once it works and the existing behavior it touches is verified unbroken. Small, self-contained changes can go straight to `main`.

## Commands

Run all commands from the repo root unless noted.

- `npm run tauri dev` — launches the full app (Vite dev server + Rust backend compiled and run in a native window). This is the primary way to run the app during development; it hot-reloads the frontend and recompiles/restarts the Rust backend on file changes.
- `npm run dev` — Vite dev server only (frontend in a browser tab, no Tauri window/backend). Rarely useful alone since the app needs the Rust backend to do anything.
- `npm run build` — type-checks (`tsc`) then builds the frontend for production.
- `npx tsc --noEmit` — type-check the frontend without emitting; run this after any TypeScript change.
- `cd src-tauri && cargo test` — runs the Rust test suite (all tests are inline `#[cfg(test)] mod tests` blocks next to the code they test, no separate `tests/` directory). Run a single test with `cargo test <test_name>`; add `-- --nocapture` to see `eprintln!`/`println!` output.
- `cd src-tauri && cargo build` — compile the Rust backend without running it; useful for a fast correctness check.

There is no separate lint command configured (no ESLint/Clippy CI step); rely on `tsc --noEmit` and `cargo test`/`cargo build` for correctness.

### Windows dev-server gotcha

`npm run tauri dev` runs as a long-lived background process. If it's stopped abruptly (e.g. killing the task without a clean shutdown), the Vite process holding port 1420 and/or the compiled `d-craft.exe` can survive as orphaned processes. If a subsequent `npm run tauri dev` fails to bind port 1420 or behaves oddly, kill any stale `node`/`d-craft.exe` processes before relaunching.

Because `cargo test`/`cargo build`/`cargo add` share the same `target/` directory as the running dev server's file-watcher-triggered `cargo run`, running them concurrently with `tauri dev` active can cause transient, spurious compile errors (build-cache lock contention). If the dev server's log shows a confusing error right after you ran a manual cargo command, re-run `cargo build` standalone to check whether the source is actually fine before investigating further — it usually is, and the dev server recovers on its next file-triggered rebuild.

## Architecture

**Split of responsibility**: Rust (`src-tauri/src/`) owns all geometry/document state and is the single source of truth; the frontend (`src/`, TypeScript + three.js) owns rendering, camera, and tool/mouse interaction, and talks to Rust exclusively through Tauri `#[tauri::command]` functions in `commands.rs`. Every mutating command returns a full `DocumentSnapshot` (triangulated geometry + boundary loops + groups + selection) that the frontend uses to redraw. There's no incremental diffing — documents are small enough that resending everything each time is simpler and fast enough.

**Z-up world convention** throughout (matches SketchUp and STL/3D-printing slicer conventions), not the Y-up convention common in other three.js apps.

**1 world unit = 1 mm** throughout (STL itself is unitless, but every slicer assumes mm on import, so this keeps export conversion-free). Purely a modeling/UI convention — geometry code has no notion of units — but it's why the ground grid is sized 100×100 in 10-unit cells and the measurement HUD labels values "mm".

### Rust backend (`src-tauri/src/`)

- `geometry/mesh.rs` — the core data model: `Mesh` holds `SlotMap<VertexId, Vertex>` and `SlotMap<FaceId, Face>` (generational-index arenas via the `slotmap` crate). A `Face` is an `outer` vertex-ID loop plus zero or more `holes` loops. **Winding is a hard invariant**: `outer` must be wound counter-clockwise as seen from `Face.normal`; every loop in `holes` must be wound the opposite way (clockwise). Faces do not share topology/vertices across unrelated draw/push-pull operations, which is what makes push/pull, erase, and export simple.
- `geometry/plane.rs` — `Plane::from_normal(origin, normal)` builds an orthonormal right-handed `(u, v, normal)` basis for projecting 3D loop points into a 2D local coordinate system and back (`to_2d`/`to_3d`). Used everywhere a face needs 2D processing (drawing, triangulation, inset). The basis is a pure function of `normal` alone (translation-independent), so two `Plane`s built from the same normal but different origins always agree on orientation — this is relied on implicitly in several places.
- `geometry/face_detect.rs` — given a coplanar 2D point/edge graph, traces boundary loops (half-edge "rotate to next-clockwise neighbor" algorithm) and nests them by containment into faces-with-holes. This is what makes drawing a closed loop inside an existing coplanar face auto-split it ("sticky geometry" — SketchUp's term). Only keeps positive-area (CCW) cycles as candidate loops, then **must reverse a loop before storing it as a hole** to satisfy `mesh.rs`'s winding invariant (a real bug here — hole loops stored unreversed — caused silently overlapping/wrong triangulation on any non-symmetric hole shape; see the git history around inset-tool fixes for the failure mode if touching this code). Finally, `merge_holes_sharing_an_edge` fuses any two of a face's hole loops that run along a shared edge into the single loop tracing their union. Two *regions* adjacent along an edge are correctly two cycles (each may independently become a face or stay empty), but as *holes of the face around them* they describe one connected uncovered area, and two loops is wrong data rather than an unusual encoding: `triangulate_face` bridges each hole to the nearest polygon vertex, so the second bridge lands on a vertex the first hole already contributed (distance zero), yielding a self-touching polygon ear-clipping bails out of — a partial triangulation, i.e. open edges downstream plus a visibly missing chunk on render/export. `pushpull` would likewise raise one wall per loop and duplicate the shared edge, which is why this is fixed once here rather than in each consumer. Only edge-sharing is handled; loops meeting at a single vertex pinch to a figure-eight no simple loop represents, and no draw tool produces that without also sharing an edge.
- `geometry/triangulate.rs` — ear-clipping triangulation of a (possibly holed) face. Holes are merged into the outer loop via nearest-vertex bridging before ear-clipping — this is a simple heuristic, not a general visibility-safe bridge, and depends on holes being correctly wound opposite the outer loop. `point_in_triangle`'s strict (non-boundary-inclusive) containment is deliberate for hole-bridging (a boundary-inclusive test would see the bridge's duplicate vertices as "inside" and block every ear near it) but has a second, separate failure mode on a boundary with three exactly-collinear consecutive vertices (produced by `face_detect::split_edges_at_interior_points`, see below): the strict test lets an ear's new diagonal cut straight past the middle vertex instead of being blocked by it, since a point *on* that diagonal isn't strictly *inside* the ear triangle. `on_segment_interior` is the separate, targeted check for exactly that case — a vertex sitting on the ear's new (prev, next) edge blocks the ear, without affecting the bridge-duplicate case (which sits on the *other* two edges, not the new diagonal). Skipping this produces a triangle edge that doesn't correspond to any real boundary edge, which reads as an open edge to `check_manifold` despite the face's own boundary loop being completely correct — a real bug found via the corner-stud T-junction fix below, and the reason that fix needed changes in three different files, not just `face_detect.rs`.
- `geometry/pushpull.rs` — extrudes a flat face into a solid (or a face-with-holes into a hollow tube). Winding is sign-aware so normals always face outward regardless of push vs. pull direction. Two variants: `push_pull` (standalone sketch face → new closed solid, caps at both ends) and `push_pull_attached` (a face already on a solid's boundary → **no cap at the source position**, always-forward winding, so pulling a solid's cap extends it into one merged watertight shell and pushing inward carves a recess; `Document::push_pull` picks the variant from `solid_face_ids` membership). Emitting a source cap for an attached face would leave a coincident interior cap whose edges triple up and break manifoldness — the bug class the attached variant exists to prevent. `is_manifold` checks watertightness (every triangulated edge appears exactly once in each direction) — note this does *not* catch 2D self-overlap within a single face's own triangulation, only 3D edge-pairing.
- `geometry/inset.rs` — per-edge miter polygon offset (not a true straight skeleton), used by the Inset tool. Rejects offsets that would collapse or invert the polygon rather than returning self-intersecting geometry.
- `geometry/primitives.rs` — rectangle/circle/polyline-loop face construction on a `Plane`.
- `scene/document.rs` — `Document` is the whole editable model: `mesh: Mesh`, `groups: SlotMap<GroupId, Group>`, `selection: Selection`, `guides: Vec<Guide>`, plus private `face_to_group` and `solid_face_ids` bookkeeping. A `Guide` (`{ a, b }`, both `DVec3`) is the segment left behind by the Measure tool — a reference-only annotation that never enters `Mesh`, so it's automatically invisible to triangulation, STL export, `check_model`, bounding boxes, and `connected_components`. Guides are deliberately world-fixed: no transform command (`translate_faces`/`rotate_faces`/`scale_faces`/`drop_to_plate`/`arrange_for_print`) moves them, since there's no non-arbitrary rule for which guides "belong" to a moved face set and the primary workflow — measure on one part, move it aside, build the next part on the marks — depends on them staying put. Draw operations (`draw_rectangle`/`draw_circle`/`draw_polygon`) all follow the same pattern: build a temp face, extract its loop, delete the temp face, then call `resplit` to fold it into the existing geometry and re-run `face_detect`. `resplit` dispatches on an optional `target_face_id`: `None` (or a stale id no longer in the mesh — falls back rather than dropping the drawn shape) goes to `resplit_plane`, a *document-wide* coplanar search (this is what makes drawing a loop inside an existing coplanar face auto-split it, and also means `solid_face_ids` faces — created by push/pull — must be excluded from that search, or an already-extruded solid's cap sitting exactly on another drawing plane would get swept into an unrelated sketch); a live target id goes to `resplit_face_with_loops`, which only resplits *that one face's own* boundary/holes — this is what lets a sketch be drawn directly on an existing solid's side wall (a porthole/hatch outline) without disturbing any other coplanar geometry, solid or not. `inset_face` is just `resplit_face_with_loops` with the inset loop as the one extra loop. Both paths propagate the source face's group/solid-boundary membership onto whatever faces they produce. `duplicate_faces`/`mirror_faces`/`array_faces` go through `clone_faces_mapped`, which clones a face set through one shared old-vertex→new-vertex map (so a solid's shared edges stay shared in the copy, keeping it independently manifold); `mirror_faces` reflects positions across a `MirrorAxis` plane through a pivot and reverses every cloned loop, since a reflection alone would flip normals inward — reversal is what restores the CCW-outer/CW-hole invariant afterward. Mirroring produces a new copy and leaves the source untouched, matching SketchUp's Mirror. `array_faces` calls `clone_faces_mapped` once per grid cell (translation only, so never `reverse_winding`) to tile the selection into a columns×rows grid stepping along world X/Y; the counts include the source, which stays in cell (0, 0). It exists as a backend command rather than a frontend loop over `duplicate_faces` specifically so the whole grid is one `history.record()` step, and it's the one clone operation that leaves the *source plus copies* selected (the grid, not any one copy, is the result). `commands::array_faces` caps the cell count (`MAX_ARRAY_CELLS`) before recording, so a mistyped `300 x 200` errors instead of hanging the app.
- **`resplit_loops`/`resplit_face_with_loops`/`resplit_plane` robustness** (`document.rs`): five defenses against a real "drew a shape whose corner lands on an existing vertex → the face it was drawn on comes back warped, vanishes, or leaves an open edge" class of bug, found while adding guide-snapping (a snap that deliberately invites clicking exactly on existing geometry, which made this easy to trigger). All share `Mesh::WELD_TOLERANCE` (1e-3mm) as the "same point" threshold — far above the rounding error a coordinate picks up round-tripping through the f32 `DocumentSnapshot` (endpoint/edge/guide snapping only ever sends the frontend raw coordinates, never a `VertexId`, so a corner snapped onto existing geometry is *always* a brand-new vertex at a position a hair off the original's true f64 value) and far below any feature this app's use case would draw. (1) `resplit_loops` welds vertices within tolerance into the same local 2D point before running `face_detect` — without it, the neighbor-angle sort sees two almost-coincident points and produces an arbitrary ordering between them, splicing unrelated edges into a self-intersecting face. Loops are welded in the order the caller built them (source face's own boundary first, new loop last), so a match always keeps the pre-existing vertex. (2) `resplit_face_with_loops` rejects (no-op) an `extra_loop` that doesn't fit inside the target face's own boundary (`face_detect::point_in_or_near_polygon`, tolerant of touching the boundary exactly) — the frontend resolves which face a click landed on with a single raycast, which is ambiguous exactly on a vertex/edge shared between two faces (precisely where a snapped corner is likely to land), and a loop sized for the *wrong* neighboring face's screen gesture ends up with edges crossing the target face's boundary instead of merely touching it. (3) `resplit_face_with_loops` also welds each `extra_loop` against `connected_component_vertices(face_id)` — every vertex in the *whole connected solid* `face_id` belongs to, not just `face_id`'s own boundary — before building `loops`, via `weld_loop_onto`. This is what makes a "staircase" build work: sketching on one face, snapping a corner onto an existing vertex, pushing/pulling into a stud, then separately sketching on the *adjacent* face and snapping another corner onto that same vertex - two *separate* `resplit_face_with_loops` calls, so (1)'s within-one-call weld alone can't connect them. Deliberately scoped to the connected solid rather than the whole mesh: an earlier version welded at raw vertex-creation time (`Mesh::add_vertex_welded`, since removed) mesh-wide, which incorrectly merged unrelated, independently-drawn objects that happened to share a coordinate (e.g. two separate parts both starting at the origin) — `arrange_for_print_has_no_pairwise_overlap_across_varied_part_sizes` is the regression test that caught it. `resplit_plane`'s own coplanar-and-non-solid-excluded scoping already handles its version of this correctly and was left untouched. (4) `face_detect::split_edges_at_interior_points` splits an existing edge at any other point that lands on its interior (a T-junction) before `trace_ccw_loops` runs — without it, a new loop sharing part of an edge with the face it's drawn on (most basically: a rectangle sketched flush into the corner of a larger rectangular face, the everyday "stud in the corner of a box top" move) leaves the long original edge and the new short edge exactly collinear and overlapping for part of their length, which the neighbor-angle sort has no tiebreaker for **and no way to represent at all** even with one, since nothing in the graph marks where the long edge should stop. This was originally (wrongly) treated as an unfixable tie and only safely rejected as a no-op, which itself was a regression the first time it shipped — see the git history around `a_rectangle_sharing_a_corner_with_its_target_face_splits_it_correctly` for that whole arc. Getting this right on a `face_id` that's already on a solid's boundary needed two more pieces, both found only by testing an *actual push/pull* on top of the split, not just the flat split itself: `Document::propagate_boundary_split_to_solid_siblings` inserts the same new T-junction vertex into every OTHER face of the same connected solid that shares the now-split edge (e.g. the wall below a box's top cap) — faces here don't share topology (see `Mesh`'s struct doc comment), so splitting only `face_id`'s own side of a shared rim leaves the neighbor's untouched edge with no matching reverse-direction pairing anywhere, an open edge. And `triangulate.rs`'s `on_segment_interior` check (see that file's entry above) stops ear-clipping from silently cutting a diagonal straight past the new T-junction vertex on the resulting three-collinear-vertices boundary — a bug that produces a phantom open edge even when the boundary loop itself is perfectly correct, and the reason `check_model`/`pushpull::is_manifold` are what actually catch regressions here, not the loop/vertex data alone. (5) Both `resplit_face_with_loops` and `resplit_plane` now run `resplit_loops` *before* erasing the source face(s): if `face_detect` still comes back with nothing (defense-in-depth for any remaining degenerate configuration none of the above catches), the source geometry is left untouched instead of being deleted with nothing to replace it. Without this ordering fix, *any* future `face_detect` edge case is a silent data-loss bug, not just a rejected draw. (6) `resplit_loops` decides whether a freshly detected region is a `protected_holes` entry that must stay empty via `loop_covers_any`, **not** `matches_any_loop` — the T-junction split in (4) means a protected hole's region legitimately re-traces one or more vertices longer than the hole recorded before the split, so an exact-length comparison silently stops matching and refills it (a sketch snapped onto an existing stud's rim did exactly this, duplicating every edge the stud's wall already paired with). The two comparisons are deliberately separate functions: `matches_any_loop` also answers "did an erased face fill this hole" in `resplit_plane`, where a *smaller* candidate loop genuinely is a different loop and must not match. `loop_covers_any`'s looser test is safe in the direction that matters (a false positive drops a face) because the detected regions partition the source face's area with the hole excluded, so the only region containing *every* vertex of a hole's loop is that hole's own region.
- `commands.rs` — `History` wraps the live `Document` plus capped (100-step) linear undo/redo stacks (`Mutex<History>` is the Tauri-managed app state). Every *modeling* command calls `history.record()` (clones the document onto the undo stack, clears redo) before mutating; pure selection commands (`select_faces`, `select_group`) intentionally don't, so Ctrl+Z undoes geometry edits rather than selection changes.
- `io/project_file.rs` / `io/stl_export.rs` — `ProjectFile` is a flat, index-based serde mirror of `Document` (not a direct serialization — slotmap keys aren't meaningful across program runs) used for save/load, plus `guides: Vec<Guide>` (guides hold no ids, so unlike vertices/faces/groups they're stored directly, no re-interning needed). There's no schema-version field anywhere in this format, so **every field added after the first release must be `#[serde(default)]`** or every already-saved `project.json` fails to load — `guides` is the first example of this rule in practice. `stl_export::write_binary_stl` writes binary STL directly from triangulated faces; `commands::export_stl` refuses to export a non-manifold document.

### Frontend (`src/`)

- `state/document-store.ts` — `DocumentStore` is the frontend's mirror of the backend document. All Tauri `invoke()` calls are routed through an internal promise queue (`enqueue`) so commands fired in quick succession (e.g. a draw click immediately followed by a select click) apply and have their resulting snapshots land in call order, never racing.
- `tools/` — one class per tool (`Tool` interface: `onPointerDown/Move/Up`, `onKeyDown`, `activate`/`deactivate`), wired into a `ToolManager` that dispatches raw DOM events to whichever tool is active. Tools needing a "drag along an axis with a 2D mouse" gizmo interaction (push/pull, inset, move's axis lock) share `axis-drag.ts`'s `closestDistanceAlongAxis`. Face-targeting tools (push/pull, inset, scale, move, rotate) share the pattern: if the clicked face is part of the current selection, operate on the whole selection; otherwise operate on just the clicked face. Every drag/click-click tool (draw, push/pull, inset, move, rotate, scale) owns a `NumericBuffer` (`tools/numeric-input.ts`) so a value can be typed exactly instead of only read off the mouse — digits accumulate into a buffer that overrides the mouse-driven live value in both the preview and the commit, shown via the shared `ui/measurement-hud.ts` chip; each tool defines its own "effective value" method reconciling typed vs. mouse-driven (see e.g. `PushPullTool.effectiveDistance` for the sign convention: a plain typed number follows the current drag's sign, an explicit `-` overrides it). `move-tool.ts`'s X/Y/Z axis-lock keys are checked *before* feeding a keystroke to the numeric buffer, since `NumericBuffer` also accepts `x`/`X` as a segment separator (for the draw tools' "WxH" input) and would otherwise swallow the hotkey.
- `tools/plane.ts` — `SketchPlane` + `planeFromNormal`, an exact TS port of the backend's `Plane::from_normal` (same reference-vector/cross-product construction, kept in lockstep since a mismatch would make a shape's on-screen preview disagree with what the backend actually commits). `resolveSketchTarget` is what a draw tool's first click resolves against: a raycast hit on existing geometry sketches directly on that face's own plane (and threads the hit face's id through as `target_face_id`, see below); a miss falls back to the ground plane, mirroring the backend's own stale-target fallback.
- `tools/draw-tool.ts` — all three draw tools (rectangle/circle/polygon) resolve and lock a `SketchPlane` on their first click/point, so a shape can be sketched directly on an existing solid's face (not just the ground plane) — this is what unlocks side-of-hull greebles like portholes: sketch on the wall, then Push/Pull the cut face inward. The locked plane's `faceId`, if any, is passed as `target_face_id` to the draw command.
- `tools/snapping.ts` — endpoint/midpoint/edge snapping for draw tools, computed entirely client-side from the already-available `DocumentSnapshot` (not a backend round-trip) since the frontend already holds full geometry after every command. `findPlanarSnap` takes any `SketchPlane`, not just the ground plane, so snapping works the same way whether sketching on the ground or on an existing face. Measure-tool guides participate in every tier (endpoint/midpoint/edge) of both `findPlanarSnap` and the unconstrained `findSnap3d` under one shared `"guide"` `SnapKind` — a guide endpoint and a model vertex are equally deliberate targets, so within a tier the nearer one wins regardless of source; there's no separate, lower-priority guide tier.
- `viewport/mesh-renderer.ts` — renders the document as one triangulated mesh plus a separate selection-highlight overlay mesh and a separate boundary-edge `LineSegments` object (drawn from `outer`/`holes` loops, not the triangulation, since ear-clip diagonals aren't real edges). Uses `flatShading: true` deliberately — faces from the same solid legitimately share vertices at hard edges, and smooth-shaded shared-vertex normals would incorrectly blend across them.
- `viewport/guide-renderer.ts` — draws Measure-tool guides as dashed `LineSegments` (color is the only reliable "not model geometry" signal available, since `LineBasicMaterial.linewidth` is ignored by ANGLE on Windows) plus a `Points` mark at each guide's two endpoints and midpoint. A separate object from `MeshRenderer` on purpose: guides carry their own world coordinates rather than indices into `snapshot.vertices`, and the whole point is that they must not be visually confused with real edges.
- `viewport/controls.ts` — custom Z-up spherical camera controls (orbit/pan/zoom), SketchUp-style mouse bindings.
- `ui/` — small vanilla-DOM UI pieces: toolbar, file save/open/export-STL menu (backed by `@tauri-apps/plugin-dialog`'s native file pickers), `measurement-hud.ts` (the bottom-center typed-value chip, see `tools/numeric-input.ts` above), and the outliner panel — groups plus a Mirror X/Y/Z action row (mirrors a *copy* of the selection across that world axis through the origin; `select-tool.ts`'s Ctrl+D duplicates the selection with a small visible offset) and an Array Copy row (cols/rows/pitch number fields driving `array_faces`; unlike Mirror it runs the selection through `expandToConnectedObjects` first, so clicking one face of a solid tiles the whole solid). All three actions leave their result selected, ready for a follow-up Move. Number `<input>`s in these panels need no shortcut guard of their own — `ToolManager`, `toolbar.ts` and `main.ts`'s keydown listeners all already ignore events targeting an `HTMLInputElement`.

### Cross-cutting invariants worth knowing before touching geometry code

- A face's `outer` loop is always CCW as seen from `normal`; every `holes` loop is always CW. Code that builds a loop and hands it to `Mesh::add_face` or stores it as a hole must preserve this.
- `Plane` bases for the same normal are identical regardless of origin — safe to build a fresh `Plane::from_normal` per-operation rather than threading one through.
- FaceIds/VertexIds can be invalidated by `resplit_plane` (drawing new coplanar geometry re-detects and recreates faces, including ones not directly involved). Frontend/tests should look up current ids from the live document rather than trusting an id returned by an earlier, unrelated operation.
